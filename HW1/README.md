docker compose up --build --wait
curl -i http://localhost:8000/health
```

```

content-type: application/json

## На что ориентируемся
1. Лента и карточки товаров явно запрашиваются в разы чаще, чем оформляются заказы => пиковая нагрузка на чтение
2. Продукт получится довольно большим, поэтому над ним могут одновременно работать несколько команд => релиз одной команды не должен рисковать работой других сервисов
3. Нужно особенным образом обезопасить платежные данные клиентов, доступ к ним должен быть у минимального количества разработчиков
4. Заказ могут сформировать сразу на несколько продавцов => статусы доставки и выплаты дожны вестись по отправителям отдельно. Отмену заказа разрешаем только целиком, пока никто из продавцов ничего еще не отправил.
5. Персонализация это очень важная часть, которая активно будет применять ML. Пока что для анонимных пользователей будем показывать популярные за 7 дней товары + новинки. Для авторизованного пользователя будем строить профиль интересов с весами разных категорий и брендов. Веса будут обновляться за счет просмотров карточек, кликов и добавлений в корзину, а также уменьшаться со временем. Такие сигналы будет посылать витрина в feed service, покупки feed узнает из событий заказов. Ранжировать кандидатов в ленту будем просто линейной регрессией с учетом интереса, популярности товара и новизны. Переход к другим алгоритмам не затронет другие сервисы.
6. Всякую логистику, доставку, отзывы, модерацию и админку не реализовывал, их можно добавить абсолютно аналогично остальным доменам.

## Домены
1. Пользователи и доступ -> User Service -> Регистрация и вход, выдача JWT, роли (покупатель / продавец), профили покупателей (имя, адреса, контакты), профили продавцов (магазин, статус)
2. Каталог -> Catalog Service -> Товары и карточки, категории, изображения, цены, остатки, их резервирование и подтверждение
3. Лента и персонализация -> Feed Service -> Поведенческие сигналы по типу кликов, профили интересов, подбор и ранжирование товаров в ленте
4. Заказы -> Order Service -> Корзина, оформление заказа, разбиение на отправления по продавцам, статусы заказа и отправлений
5. Платежи -> Payment Service -> Создание платежа у провайдера, фиксация результата, возвраты, комиссия маркетплейса, выплаты продавцам, реквизиты продавцов
6. Уведомления -> Notification Service -> Шаблоны, отправка по событиям заказа, настройки пользователя, журнал доставки и повторы
Без отдельной доменной логики остаются витрина, кабинет продавца (клиентские странички), API gateway, kafka. Заказы считают, сколько должен заплатить покупатель, а платежи считают как именно деньги распределятся (комиссия нашего amazing сервиса, доля продавца по каждому отправлению) и ведут их учет.

В целом я постарался сделать так, чтобы один домен соответствовал одному сервису. Граница проходит именно там где у данных своя модель, своя команда владелец, свой профиль нагрузки и надежности. Владение данными и бизнес логика разбиты по этим доменам. Корзина располагается внутри Order service, так как это просто черновик заказа с теми же данными и тем же владельцем. Отдельный сервис добавил бы лишнюю нагрузку на сеть на каждом шаге оформления заказа без логического выигрыша. Смысл сделать это будет только если корзина заимеет доп функциональность, например общие корзины или подарки там.

Реквизиты продавца храним внутри Payment service, чтобы все чувствительные данные были изолированы в одном сервисе и в одной БД, поэтому мы соблюдаем максимальную приватность.

Ленту было важно сделать отдельно от каталога, потому что каталог это источник истины с записью от продавцов, а лента обслуживает именно нагрузку на чтение. Поэтому у них разные хранилища, для ленты используется opensearch + redis, а для каталога postgres.

## Владение данными

У каждого сервиса свои хранилища. В чужую БД напрямую никто не ходит. Если нужны данные другого сервиса, получаем их через его API или события Kafka.

User хранит в PostgreSQL учетные записи, хэши паролей, роли, профили и адреса. У Catalog своя PostgreSQL с товарами, категориями, ценами, остатками и резервами. Изображения лежат отдельно в хранилище с S3 API. Order хранит корзины, заказы, отправления и цены на момент покупки. Payment хранит платежи, возвраты, проводки, комиссии, выплаты и реквизиты продавцов. Notification хранит настройки, шаблоны, копию контактов, журнал отправок и задания на повторную доставку. У каждого из этих сервисов отдельная PostgreSQL.

Feed использует OpenSearch для копии каталога, по которой подбираются товары. В Redis лежат интересы пользователей, популярность товаров и кэш готовых лент. Копия каталога может немного отставать, поэтому при оформлении заказа все равно проверяем цены и наличие через Catalog. Цены покупки сохраняем в Order, иначе изменение цены продавцом поменяло бы уже оформленный заказ.

## Взаимодействие сервисов

Витрина и кабинет продавца отправляют запросы в Gateway по HTTPS с JSON. Envoy проверяет JWT и передает запрос нужному сервису. Регистрация, вход и просмотр общедоступных товаров работают без токена. Права на конкретные объекты проверяют сами сервисы. Например, продавец с валидным JWT все равно не должен иметь возможность изменить чужой товар. Между сервисами используем REST по HTTPS с JSON.

Order вызывает Catalog для резервирования и списания товаров, а Payment для создания платежа. Payment обращается к платежному провайдеру, Notification обращается к провайдерам email, SMS и push. Эти вызовы синхронные, потому что нужно получить результат операции.

Результат оплаты провайдер присылает через webhook. Gateway передает его в Payment, который проверяет подпись провайдера. Пользовательского JWT у этого запроса нет.

События передаем через Kafka. User публикует user.events, по которым Notification обновляет контакты. Catalog публикует catalog.events, по которым Feed обновляет свою копию товаров. Order публикует order.events для Catalog, Payment, Feed и Notification. Payment публикует payment.events для Order. Каждый сервис обрабатывает только нужные ему типы событий. Например после подтверждения заказа нужно отправить уведомление и учесть покупку в рекомендациях. Order публикует событие, а Notification и Feed дальше делают свою работу независимо. Если уведомления временно не работают, заказ все равно можно оформить. После восстановления Notification прочитает события, если они еще хранятся в Kafka.

На диаграмме сплошные стрелки показывают синхронные запросы от инициатора к получателю. Пунктирные показывают направление передачи событий через Kafka, точечная показывает webhook провайдера. Голубые блоки относятся к маркетплейсу, серые обозначают внешние системы, цилиндрами показаны хранилища.

## Оформление заказа

Order создает заказ в состоянии ожидания и просит Catalog зарезервировать товары. Catalog проверяет остатки и возвращает актуальные цены. Order сохраняет состав заказа, считает сумму и разбивает заказ на отправления по продавцам. Затем Payment создает платеж у провайдера, а пользователь получает ссылку на оплату. После оплаты Payment получает webhook, сохраняет результат и публикует событие. Order читает его и просит Catalog подтвердить списание товаров. Резерв к этому моменту мог истечь. Если товары еще есть, Catalog повторно резервирует и сразу списывает их. Если товаров уже нет, запускаем возврат денег. Проверка наличия и списание выполняются атомарно внутри Catalog. После подтверждения заказа Notification сообщает об этом пользователю, а Feed учитывает покупку. Продавцы выставляют статусы своих отправлений через кабинет. После доставки Payment выполняет выплату соответствующему продавцу с учетом комиссии.

Отмена разрешена только целиком и пока ничего не отправлено. При отмене освобождаем резерв или восстанавливаем остатки, а списанные деньги возвращаем. Отмена и отправка атомарно проверяют и меняют состояние заказа внутри Order, чтобы обе операции не могли одновременно успешно выполниться. Общей транзакции между заказом, резервом и платежом нет. Поэтому оформление разбито на шаги. Если продолжить не получилось, отменяем уже выполненные действия, например освобождаем товары или возвращаем деньги.

Чтобы не потерять событие, сохраняем его в БД вместе с изменением данных, а потом отдельный процесс отправляет его в Kafka. Событие может прийти повторно, поэтому обработчики проверяют его идентификатор и текущее состояние объекта. Для денежных операций передаем провайдеру постоянный ключ конкретной операции, чтобы повтор запроса не привел к повторному списанию или выплате. Неудачные уведомления повторяем, после исчерпания попыток сохраняем ошибку в журнале.

## Какие еще варианты были

### Модульный монолит

Можно разместить все домены в одном приложении, разделить код на модули и использовать одну PostgreSQL с отдельными схемами. Это проще разрабатывать, запускать и отлаживать. Между модулями нет сетевых запросов, а связанные изменения внутренних данных можно выполнить одной транзакцией. Но релиз будет общим для всех команд. При росте нагрузки на ленту придется масштабировать все приложение, а ошибка в одном модуле может повлиять на остальные.

Для небольшой команды и первого MVP я бы выбрал этот вариант. Сбои платежного провайдера все равно придется обрабатывать отдельно, потому что транзакция PostgreSQL не распространяется на внешнюю систему.

### Общее ядро + отдельные лента и уведомления

Можно объединить пользователей, каталог, заказы и платежи в Commerce Core с общей БД. Feed и Notification оставить отдельными сервисами со своими хранилищами и событиями через Kafka. Оформление заказа станет проще, потому что заказ и остатки находятся внутри одного приложения. При этом ленту можно независимо менять и масштабировать.

Но команды основных доменов все еще выпускают общее приложение. Платежные данные находятся рядом с остальной логикой ядра, поэтому изолировать доступ к ним сложнее. При этом Kafka и обновление копий данных уже нужно поддерживать.

### Отдельный сервис на каждый домен

Это вариант на диаграмме. Можно отдельно масштабировать ленту, независимо выпускать сервисы и ограничивать доступ к платежным данным. Падение уведомлений не блокирует оформление заказа. Зато приложений и хранилищ больше, запуск и отладка сложнее. Нужно учитывать сетевые ошибки, повторы событий и ситуации, когда часть оформления уже выполнена, а часть еще нет. Общей транзакции между сервисами нет, копии данных обновляются с задержкой.

Я ориентируюсь на несколько команд, большую нагрузку на чтение и частые изменения персонализации. Поэтому возможность отдельно выпускать и масштабировать сервисы здесь важнее простоты запуска. Поддерживать такую систему сложнее. Понадобятся общие логи, метрики и отслеживание запросов между сервисами. Для маленького MVP одной командой я бы выбрал монолит, но при наших предположениях отдельные сервисы выглядят оправданно.
